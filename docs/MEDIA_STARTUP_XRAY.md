# Media startup: lot 1 operations and diagnostics

Implementation and measurements: [lot1-result](audits/media-startup-opus/lot1-result.md).
This runbook proposes production actions; none were applied during implementation.

## Request and loop timing

Every `/api/*` response generated by the API has numeric-only `Server-Timing`:

- `auth`: time spent resolving session cookies, including its occasional commit;
- `db`: SQL cursor execution plus successful commit overhead (including WAL flush),
  excluding pool checkout and rollback. Failed queries/commits are not included;
- `app`: total elapsed until response headers, including auth, DB, pool/thread waits
  and provider HEAD. It excludes streaming the response body.

These spans overlap: **do not add auth + db + app**. They do not include Funnel's
separate auth subrequest or client/network time. nginx-generated errors have no API
header. No SQL, URL, object id or credential is included in these spans.

The per-worker loop sampler wakes every 100 ms; it logs individual lags >=100 ms
and a summary every minute. Samples are bounded (600, filtered to the last 60 s).
`GET /api/v1/auth/xray` requires a live admin session and returns p50/p99/max,
sample count, lifetime max and cumulative >=100 ms count. Restart resets counters.
For a long stall, sample count falls: a single sample records the full stall.

An admin can add `?xray=1` to the current screen. The overlay observes the initial
resource waterfall and resets at SPA navigation, displaying the last 80 completed
resources, relative start, duration and the three allowlisted Server-Timing spans.
It polls loop counters every 10 s. Labels are fixed categories (Identity, Library,
Media, API, Image, App resource, External resource): URLs, queries, ids and server
descriptions never enter displayed state. There is no beacon, upload or storage.
The browser's own Resource Timing buffer still contains the original resources;
the overlay does not clear it or modify application requests. Resources before
browser buffer eviction cannot be recovered. Cache hits may report zero durations
or omit server spans. Disable by removing the query parameter.

## Manual nginx application after an authorized release

Both front doors have versioned cache policy and timing logs. `ship.sh` does not
automatically apply these configuration changes:

- LAN: `nginx/nginx.conf` (`main` log format) and `nginx/conf.d/default.conf`.
- Funnel: `ops/tailscale/nginx.conf` (`media_timing`, included in nginx's http
  context). It logs request time, upstream connect and upstream response time.

At a separately authorized deployment, validate **both** effective configurations
with `nginx -t` inside their containers before reload/recreation. Follow
[REPO_WORKFLOW](REPO_WORKFLOW.md), including the separate Funnel compose project.
No local nginx/Docker executable was available for container syntax validation.
Inspect log p50/p95 by normalized route and compare API app timing with nginx
request/upstream timing. Do not export raw request logs containing private paths.

Backend cache URLs include `?v=<checksum_sha256[:12]>` when a valid stored SHA-256
is known. Only a version matching the entry's current checksum receives
`Cache-Control: private, max-age=31536000, immutable`. Missing/stale versions and
entries without a valid checksum return the current bytes with `private, no-cache`;
there is no redirect or additional SQL lookup. The common builder accepts the full
entry so all producers can supply its checksum without a query per URL.

Both `/internal-media-cache/` locations preserve the backend Cache-Control on the
X-Accel response; they must not add a blanket immutable header. This also preserves
evaluation/private grant policies. Evaluation transport URLs carry the selected
entry's version too, while retaining their existing 300-second private cache limit
on a matching version; missing/stale versions use no-cache. Signed grants retain
private/no-store and their existing TTL.

An entry id can survive a content replacement (durable poster refresh). Every byte
replacement must also update its checksum: the next status/batch then yields a new
URL. A metadata/path change with identical verified bytes keeps the version. Entries
without checksums (including current browser-upload registrations) remain
revalidatable; this change does not hash files on the read path or backfill SQL.

Posters/proxies already cached privately can remain viewable after access revocation
until browser eviction. Previously cached unversioned immutable responses cannot be
retroactively expired by the server: newly returned versioned URLs bypass them.
Shared caches must never store these private responses.

## Proposed Postgres 16 settings — DO NOT apply as part of this lot

Review these with the operator and measure overhead before a future activation:

```conf
log_lock_waits = on
track_io_timing = on
track_wal_io_timing = on
```

Keep the current `deadlock_timeout` initially. `log_lock_waits` only reports waits
beyond that threshold; normal interactive queue creation now stops lock waits at
500 ms, so its shorter waits may not appear. Query `SHOW` / `pg_settings` to check
effective values and whether a reload is required in the deployed setup. Prefer
a reviewed versioned Postgres config change and authorized reload; no ALTER SYSTEM,
reload, restart or production write was performed here. I/O timing has platform
overhead; compare `pg_test_timing` and load before enabling broadly.

After a future rollout, inspect `pg_stat_activity`, waiting advisory locks,
`pg_stat_database` commits and idle-in-transaction terminations; compare per-worker
loop p99 and poster app/db durations under a normal `/dives` load. Avoid extrapolating
local SSD timings to the production HDD. No SQL migration is required for lot 1.

## Boundaries and failure behavior

Status selectors are read-only; an expired job stays visible until the next lease
or maintenance/job-creation pass. Creation keeps queue serialization with a local
500 ms lock timeout, returning 503 + Retry-After: 1 on advisory/row-lock timeout.
Lease serialization remains intact. Synchronous route/dependency execution uses
FastAPI's threadpool and preserves the existing request session's `db.info` access
context. The SQL pool/threadpool can still queue under load; their waits appear in
app timing, not db timing.

The WebSocket is mounted outside the router's SQL dependencies. Its short handshake
session runs in the threadpool and enforces the same enabled-auth admin boundary;
no session remains borrowed for the connection lifetime. There is no new continuous
revalidation of an already accepted socket (existing behavior).
